# Groundhog Day standalone status service — run 003

Fresh implementation from this contract only; do not read another run, old source, history, evaluator, or web. Python standard library plus browser-native HTML/CSS/JS only. No package installation, external services, authentication, or deployment. Write implementation and run instructions in builder-output/. Execute it on Priory later; do not alter any existing workloads.

## Goal and failure boundary

A runnable status service monitors an explicit registry of HTTP dependencies and publishes an independently serveable static public site. The monitor and its SQLite database may be offline while the published site still loads and reveals aging evidence. No dependency on monitored services for assets or page requests. Public output must not expose probe URLs, response bodies, private headers, filesystem paths, stack traces or credentials. No automatic external messaging.

## Stable command/input boundary

`python3 status.py collect --config CONFIG --db DB --output DIR [--now UTC_ISO]`: one observation per registered service via HTTP GET with configured finite timeout; save transactionally; export public files atomically. Exit 0 even when dependencies fail (a completed observation cycle); invalid config/DB/export errors must be nonzero. Non-2xx HTTP responses are observations, not a process crash. `expected_codes` and all configured `keywords` must match; keyword comparison may be case insensitive. HTTP failure or missing keyword is impaired. Network/timeout failure is impaired with safe explanatory text, not healthy. Persist each observation timestamp, outcome, HTTP code if available, elapsed milliseconds, and safe failure reason. Never retain response bodies or secrets.

`python3 status.py export --config CONFIG --db DB --output DIR [--now UTC_ISO]`: no probes, render state at supplied/current UTC time. A newly registered service with no observations is unknown. Missing or older-than `stale_after_seconds` evidence is unknown, retaining last known observation and timestamp without presenting it as current health. Fresh success is healthy; fresh failure impaired; equality at freshness limit may remain fresh. Recovery occurs on the next fresh success, no debounce.

`python3 status.py run --config CONFIG --db DB --output DIR --interval SECONDS --iterations N`: N cycles, sleep between, same behavior as collect. Also support omitted --iterations for an operator-controlled continuous loop; Ctrl-C should stop it cleanly. No system-service installation. Interval, timeout and staleness are explicit operator-selected settings, not user-prescribed defaults.

Config JSON: `title`, `support_url`, `services` array. Each service has `id`, `name`, `url`, `kind` (first_party or provider_reachability), `impact` (customer-readable scope), `expected_codes` (integer list), `keywords` (string list), `timeout_seconds` (positive), `stale_after_seconds` (positive). Validate duplicate/empty ids, empty registry, unsupported schemes (only http/https), invalid status/policy values. Do not accept URL userinfo. Treat config strings as untrusted; HTML escape them; support URL must be https or mailto, not script/file. Synthetic test config URLs are loopback only. This executable supports real public endpoint configuration but tests never contact providers.

Use SQLite durable observations and transition incidents. Consecutive failures do not create duplicate incidents. First failure opens an incident; next success resolves it with evidence timestamps. Restarting/re-exporting preserves history. Unknown/stale presentation does not falsely mark an incident resolved. Safe config removal stops displaying that service and its events in public output; private historical DB retention may remain. Keep modest historical data for the experiment; no unbounded process-memory state.

## Public boundary

Export `index.html` plus `status.json`, self-contained with no network assets. JSON includes `generated_at`, `services`, `incidents`. Each service exposes `id`, `name`, `kind`, `impact`, `state` (healthy/impaired/unknown), `observed_at` (null if absent), `http_status`, `description`, `stale_after_seconds`, and `history` (ordered observations, safe fields, enough for the test sequence). Incident fields: `service_id`, `opened_at`, `resolved_at` (nullable), safe description. No URL/body from probe.

The HTML renders current services, meaningful healthy/impaired/unknown text with green/red/amber distinction, time for each observation, per-service impact and evidence limits, incident history and a visible support link even when all checks are green. A noncritical outage must not announce that every wash is down. A green provider reachability check explicitly does not prove account credentials or end-to-end business health. No promises of staff action or recovery ETA. A scoped summary says e.g. some listed checks impaired/unknown, not all operations unavailable.

For independent browser evaluation each visible service card has `data-service-id` and `data-state`. Have its `.state` element visibly say Healthy/Impaired/Unknown and use a computed green/red/amber or corresponding background; state isn't conveyed by color alone. Show timestamp in time[datetime]. Link support with id="support-link". Embed only safe public model in script id="status-data" type="application/json"; escape HTML script terminators. Browser JS reassesses freshness using Date.now at load and at least every second, changes state to unknown when evidence ages, and shows a banner that the snapshot may be out of date if generated_at ages. Never reset data age merely by reloading. No-JS view clearly labels statuses as snapshot observations and cannot claim current live health. Follow accessible, readable phone/square/tablet layout; no horizontal overflow. Support is an actual configured navigable destination (tests use safe example.invalid), not a fake message saying help is available without a route.

## Run 003 extension: alert and open-page continuity boundary

Implement from the full contract above in a fresh context, not a previous implementation. These additions close observed replacement-capability gaps; use only synthetic loopback sinks in tests.

Config optionally adds notification_url (http/https, no userinfo) and refresh_seconds (positive finite; example choices belong to operator). With no notification_url, no delivery is attempted. With one configured, each opened/resolved incident transaction creates exactly one durable outbox event with stable id, service_id, type (opened/resolved), observed_at and safe description. After collect and on each monitor cycle, POST pending events as JSON to that URL with finite timeout and Content-Type application/json. Any 2xx response marks delivered; non-2xx/network error leaves pending for a later collect retry. Do not duplicate events on consecutive failures or resend delivered ones; receiver must deduplicate by stable id because delivery is at least once. Do not lose committed observations/export when sink fails. Do not include URLs/response bodies/private details. No authenticated messaging transport or real destination activated. status.json adds notification_events (id,service_id,type,observed_at,delivered boolean); exclude removed service events. This is a generic adapter boundary, not an email/GitHub integration.

When served via HTTP(S), an already-open page fetches relative status.json at the configured refresh_seconds interval (default 5 if absent, explicitly documented proposed implementation choice), replaces safe rendered component/incident data on successful valid fetch, and re-evaluates observation freshness. It must recover impaired→healthy from a new successful observation without manual reload; failed fetch cannot renew old evidence or fabricate recovery. Preserve help and provider/scope text. Static local file rendering may omit polling but still re-evaluate freshness. Do not inject untrusted model strings with innerHTML. No external asset fetch. Both HTML and model are independent of monitored dependencies; collector/sink failures leave published static files serviceable.

Provide a minimal repeatable loopback synthetic dependency/sink demo and operations instructions. Actual external notification destination and domain/hosting activation still require applicable approval, and are not executed by this experiment.

## Evaluator-discovered actionability correction

The configured support route must be prominent near the page heading or persistently available, including the initial ordinary-phone viewport, even when all checks are healthy. Requiring users to scroll past ten service cards to find it does not satisfy easy-to-find help. This clarifies the original actionability goal, not a new workflow.
