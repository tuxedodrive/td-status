## Boundary

The caller POSTs JSON to /events: id (stable nonempty string), service_id (nonempty string), type (opened or resolved), observed_at (UTC ISO string), description (safe string). HTTP 204 means every configured transport accepted delivery, not human receipt. Invalid payload → 400; wrong path → 404; failed transport → 503 (caller will retry the same event). Duplicate completed event → 204 without another side effect. No printed/logged credentials or raw downstream errors.

`python3 alert_adapter.py --config CONFIG --db DB --host 127.0.0.1 --port PORT`; bind loopback only, reject non-loopback host. PORT may be 0; print a single JSON startup line with actual bound port to stdout, flush it, then serve. Parent terminates owned process after tests. Config/schema/storage failure exits nonzero. Use a durable SQLite delivery ledger per event and transport so process restart/retry does not repeat already accepted transports; serialize event handling or lock it. At-least-once semantics remain across a crash between external acceptance and ledger commit; document this exact limitation, no impossible exactly-once email claim.

Config has optional email and github objects, at least one required. Optional service_names maps service id to a public display name. Transport settings and secrets stay outside public output. Secrets come only from explicitly named environment variables, never URL userinfo or a stored plaintext token. Missing configured auth environment variable is a startup error with no value printed.

email: smtp_host, smtp_port, from_address, to_addresses (nonempty list), starttls (boolean), optional username_env and password_env (both or neither). Allow unauthenticated/plain SMTP only for loopback SMTP host for synthetic tests; non-loopback SMTP requires starttls true and configured auth environment names. Reject CR/LF in addresses and header inputs. Use finite timeout. Subject: Service Alert: DISPLAY_NAME — opened/resolved; UTF-8 body includes service name, event type, time, description and event id. smtplib + EmailMessage; success means relay accepted recipient(s), not inbox/person receipt. If any refused recipient, fail and retain pending state. No provider-specific API selected. No assumption about production SMTP host, From identity or credentials.

github: api_base (https in production, http loopback allowed for fake tests), repository (owner/name), token_env (required), optional user_agent. Use Authorization Bearer from env, Accept application/vnd.github+json and finite timeout. On opened event, POST /repos/OWNER/REPO/issues with title Service Alert: DISPLAY_NAME, body including safe description/time/event id and stable service marker `<!-- status-service:SERVICE_ID -->`. Persist returned issue number for that service. On resolved event, PATCH /repos/OWNER/REPO/issues/NUMBER state closed, state_reason completed. Repeated opening for one active service should not create another issue; use persisted mapping. If recovery has no mapping, GET /repos/OWNER/REPO/issues?state=open&per_page=100 and find the exact marker before closing; if not found, treat GitHub recovery as no-op and acknowledge. Do not guess assignees or add permissions. Non-2xx, malformed issue response or auth error → 503 without marking that transport delivered; do not leak token/endpoint error. A service resolving after its active issue was closed must permit a new issue on a subsequent opening.

An event with both transports completes only when both succeed. If email succeeds and GitHub fails, retry must not resend accepted email. If GitHub opening succeeds, then another event retries after a server restart, use saved issue mapping. State-changing HTTP occurs only against caller-supplied fake destinations in this experiment. Document exact production inputs still needed and least necessary capability (SMTP sending; issues read/write on one repo), without creating credentials, deploying or activating external messages.

All example event data is synthetic Groundhog Day. No global installs, public listeners or system services. CLI, configuration, local runner setup and stop/restart behavior should be reproducible.
